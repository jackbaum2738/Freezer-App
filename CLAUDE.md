# Freezr — Project Memory (CLAUDE.md)

Freezr is a household shared freezer inventory app. Scan a barcode to add/remove items, synced in real time across everyone in the household. Built entirely as a single-page static web app (PWA) — no backend server of its own.

## Architecture

- **`index.html`** — the entire app. Vanilla JS (no framework, no build step), inline CSS, one big IIFE. Deliberately kept as a single file for simplicity — this is a small household tool, not a large codebase.
- **Storage/sync:** Firebase Firestore (`freezer/inventory` document), using the Firebase v10.7.1 **compat** SDK loaded via `<script>` tags from `www.gstatic.com` (not npm — no build step exists). Real-time sync via `onSnapshot`. No user auth — Firestore security rules are intentionally open (`allow read, write: if true`, scoped to the `freezer` collection only) since this is a private household tool with no login system.
- **Barcode scanning:** QuaggaJS (`quagga.min.js` from cdnjs) for live camera scanning, plus a photo-based fallback (`Quagga.decodeSingle` on a photo taken via the native camera app through a file input with `capture="environment"`) — the photo path exists specifically because live browser camera focus/torch control is unreliable across devices (especially iOS Safari), and the native camera app doesn't have that problem.
- **PWA setup:** `manifest.json`, `service-worker.js`, and icon files (`icon-192.png`, `icon-512.png`, `apple-touch-icon.png`, `favicon.png`) make it installable to the home screen on both Android and iOS.
- **Hosting:** GitHub Pages, static files only, no CI/build pipeline. Deploys are just committing files to the repo root.
- **Navigation:** bottom tab bar with two tabs — **Freezr** (❄️, the original scan/list screen, `#inventoryView`) and **Settings** (⚙️, `#settingsView`). Built to make room for a future third tab (Shopping List is the planned candidate).
- **Categories:** every item has a `category` field (string). `state.categories` is an ordered array of category names — order is user-controlled (drag-to-reorder in Settings) and that order is what every category picker in the app displays. `state.categoryColors` maps category name → hex color. `state.categoryByBarcode` maps barcode → last-used category, the same "learn per barcode" pattern already used for item names (`state.products`), so re-scanning a known barcode defaults to the same category. New item names get a category *guessed* from a keyword dictionary (`CATEGORY_KEYWORDS`/`guessCategory()`) — deliberately simple substring matching, not an LLM call, so the app stays dependency-free and works offline; editable before saving either way.
- **Category picker UI:** collapsed to a single row (current category's colored dot + name + `›` chevron) in the add-item modal, batch review rows, and item detail popup — tapping it opens a shared bottom-sheet (`categorySheetBack`/`openCategorySheet()`) showing the full set of category chips to choose from. This replaced an earlier version that showed all category chips inline at once, which took up too much space (see git history on `feature/compact-category-picker` if the old approach is ever needed for reference).
- **Category colors:** chosen from a fixed 24-swatch preset palette (`CATEGORY_COLOR_PALETTE`), never free-form — this guarantees a color is always re-selectable later. The grid is 6 columns × 4 rows: one column per hue (red/orange/yellow/green/blue/purple) running bright→medium→pastel top to bottom, plus a bottom row of neutrals (black/dark grey/grey/light grey/off-white/brown) for categories with no real hue (e.g. Bread & Bakery, Other). New categories default to the grey neutral swatch until the user picks a real color. `normalizeCategoryColors()` runs on every load and silently snaps any stored color that isn't one of the 24 current swatches onto the nearest one (by RGB distance, or the known default if the category name matches) — this exists because the palette itself was introduced *after* categories/colors first shipped, and was later reordered again, so old synced data could otherwise hold colors that no longer appear anywhere in the picker.
- **Theme:** dark (default), light, or "match device", chosen in Settings → Appearance. Stored in `localStorage` (`freezr-theme` key) — deliberately **not** synced via Firestore, since it's a personal per-device display preference, not shared household inventory data. Applied via a `data-theme` attribute on `<html>`, set by a tiny inline script at the very top of `<head>` (before the main CSS) to avoid a flash of the wrong theme on load, then re-applied/kept in sync by the main app script (which also listens for OS theme changes when "match device" is selected).

## Important design decisions (don't "fix" these — they're deliberate)

- **`service-worker.js` is intentionally a no-op** — it registers a `fetch` listener but never calls `respondWith()`. This exists purely to satisfy Android's install criteria. It does NOT cache anything, on purpose: aggressive caching previously caused stale-version bugs, and since the app is useless offline anyway (needs live Firestore), there's no upside to caching.
- **Data model:** `state.items` is a flat array of individual unit records (`{id, barcode, name, category, dateAdded, opened}`), NOT pre-grouped by quantity. The UI groups same barcode+name into one row with a "×N" badge at render time (`groupItems()`), but removal/quantity operations always work FIFO against the oldest individual unit. This was a deliberate choice to keep removal logic simple and consistent.
- **The item detail popup uses staged edits.** Name, quantity, and opened/sealed status are all held in local variables (`pendingQty`, `pendingOpened`, the name input's value) and only committed to `state.items` when Save is tapped. Close/✕ discards everything. This was a bug fix — quantity used to apply live immediately while name didn't, which was confusing and got explicitly fixed.
- **Opened/sealed status applies to the *oldest* unit in a group**, not per-unit, since the UI only exposes one toggle per grouped row. Documented simplification, not a bug.
- **Versioning scheme (semantic, restarted from 1.0.0):** `x.0.0` = major (genuinely new features/pages), `1.x.0` = minor (batches of smaller additions), `1.0.x` = patch (tiny fixes/tweaks). The version number is hardcoded in the footer of `index.html` and must be bumped by hand with every change. Full history lives in `CHANGELOG.txt` — update both together, every time.
- **Icons must be full-bleed square PNGs with square corners in the source file** — never round the corners yourself. iOS/Android apply their own mask on top, so a pre-rounded icon causes double-rounding/white-sliver artifacts. Learned this the hard way.
- **Firebase web API keys are not secret** — they're meant to be public in client-side code. Security comes from Firestore rules, not from hiding the key. The GitHub repo is public and that's fine.
- **Category drag-to-reorder uses Pointer Events, not native HTML5 drag-and-drop.** iOS Safari — the primary target device — doesn't fire native `dragstart`/`dragover` events for touch input, so a native-DnD implementation would silently not work on iPhone. The reorder logic (`attachCategoryDragHandlers()`) tracks `pointerdown`/`pointermove`/`pointerup` on a drag handle, visually follows the pointer via `transform: translateY()` on the dragged row, computes the target index by comparing the dragged row's live midpoint against sibling rows' static midpoints, and only commits the array reorder + full re-render on release.
- **Toast z-index must stay above modal z-index.** The toast was originally `z-index: 50` while modals are `z-index: 60`, so any validation toast fired while a modal was open (e.g. "That category already exists") rendered invisibly behind the modal — it looked like the action silently did nothing, when it had actually correctly been rejected. Fixed by raising the toast to `z-index: 70`. If a new overlay is ever added above modals, keep the toast above it too, or this bug comes back.
- **All local testing of `index.html` in this environment must use a stub Firestore, not the real one.** The sandbox this app has been developed in blocks outbound requests to `www.gstatic.com` and `cdnjs.cloudflare.com` (org network policy — 403, not a trust/cert issue), so Firebase and Quagga can't load in a real browser here. The working pattern: copy `index.html` to a throwaway file, replace the two Firebase `<script>` tags with a single `<script src="fake-firebase.js">` (a small in-memory Firestore emulator — `onSnapshot`/`.set()` with `merge` support is enough to exercise the real app logic unmodified), serve both over a local `python3 -m http.server`, and drive it with Playwright (`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`, `/opt/node22/lib/node_modules/playwright`). Delete the throwaway files afterward — never commit them. This has been the standard verification step for every feature/fix in this project so far.

## Known issues (unresolved, don't re-litigate without new info)

- **Safari Share-button JS error:** tapping the native iOS Share icon sometimes triggers a generic, detail-free "Script error." in the page's error banner. Extensively debugged (ruled out the async Firestore render path, ruled out the service worker) — it's very likely an opaque/masked error from something Safari itself does internally (e.g. generating the share preview), not app code. Doesn't affect any real functionality. Worth revisiting only with real Safari devtools access (e.g. via a Mac), not by guessing blind again.
- **Camera focus on some Android devices** can be unreliable through the browser (this is *why* the photo-scan fallback exists). Native camera APIs (if this ever becomes a Capacitor-wrapped native app) would likely fix this properly.

## Possible future direction: native app packaging

If this ever needs to go on the Play Store / App Store, the current architecture carries over directly — no rewrite needed:
- **Android:** Trusted Web Activity (Google's official PWA→Play Store path), lightweight.
- **iOS:** Capacitor wrapper + Apple Developer account + App Store review. Would also likely fix the camera focus/torch limitations above via native camera APIs.
This isn't being actively pursued — just documented so it's not forgotten as an option.

## Working conventions

- Keep everything in as few files as practical. Don't introduce a build step/bundler/framework without a strong reason — this is meant to stay simple enough for a non-developer to redeploy by hand if needed.
- Bump the version number + `CHANGELOG.txt` with every change, however small.
- See `freezr-app-ideas.md` in this repo for the full backlog of planned/considered features (organized into Done / Known issues / Organisation / Bigger features / Ideas). Check it before assuming something hasn't been discussed.
- **Git workflow used throughout this project:** one feature/fix per branch, cut from the latest `main` each time (never stacked on a previous feature branch once it's merged — check whether the last PR merged before branching). Push, open a PR with a Summary + Test plan (the test plan documents what was verified with the stub-Firestore Playwright setup above), and wait for the user to merge via the GitHub UI before starting the next branch. The user does the merging; don't merge PRs unprompted.
- **For any visually/interactively significant UI change (new layout, new component, reworked interaction), build a working mockup as a published Artifact first and get explicit sign-off before touching `index.html`.** This has come up repeatedly (the collapsed category-picker-with-sheet redesign, the 6×4 color grid reorder) and the user has explicitly asked for it by name ("show me what it will look like before making changes"). Match the mockup's HTML/CSS to the app's real tokens and structure (pull actual hex values and markup from `index.html` rather than approximating) so what's approved is literally what gets built. Small, unambiguous bug fixes (e.g. the toast z-index issue) don't need this — only genuine design decisions do.

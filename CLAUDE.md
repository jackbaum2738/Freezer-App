# Freezr — Project Memory (CLAUDE.md)

Freezr is a household shared freezer inventory app. Scan a barcode to add/remove items, synced in real time across everyone in the household. Built entirely as a single-page static web app (PWA) — no backend server of its own.

## Architecture

- **`index.html`** — the entire app. Vanilla JS (no framework, no build step), inline CSS, one big IIFE. Deliberately kept as a single file for simplicity — this is a small household tool, not a large codebase.
- **Storage/sync:** Firebase Firestore, one document per Freezr (`freezrs/{code}` — see "Freezr households" below), using the Firebase v10.7.1 **compat** SDK loaded via `<script>` tags from `www.gstatic.com` (not npm — no build step exists). Real-time sync via `onSnapshot`. No user auth — Firestore security rules are intentionally open (`allow read, write: if true`, scoped to the `freezrs` collection only), since anyone who knows a Freezr's code is meant to be able to read/write it — that's how join-by-code works, and there's no login system.
- **Freezr households (multi-tenancy):** the app supports separate, unrelated groups ("Freezrs") each with entirely separate items/categories/freezers/history, instead of one global shared document. On any device with no locally-saved Freezr code, a mandatory first-run screen (`freezrChoiceModalBack` — no ✕, no backdrop-dismiss, runs *before* the name prompt) offers **Join a Freezr** (enter a code, validated with a `.get()` before switching) or **Create a Freezr** (first asks for a name via `freezrNameModalBack`, then generates a memorable two-word code from `FREEZR_CODE_ADJECTIVES`/`FREEZR_CODE_NOUNS` — e.g. `FROSTY-OTTER` — retrying on collision, and writes a fresh doc via `freshFreezrDoc(name)`). The active code lives in `localStorage` (`freezr-code`), same per-device pattern as theme/display name. `connectToFreezr(code)` is the single place that attaches the Firestore listener; it unsubscribes any previous listener first (see the listener-leak fix note under Known issues/design decisions) and populates `state.freezrName` from the doc's `name` field.
- **Freezr switcher:** every Freezr ever joined or created on a device is cached locally in `localStorage` (`freezr-saved`, an array of `{code, name}`, most-recently-added first — kept in sync via `upsertSavedFreezr()` whenever a snapshot resolves). Settings → "Switch" opens `freezrSwitcherModalBack` listing them; the active one is checkmarked and can't be removed, others switch to instantly (no re-typing the code) or can be forgotten from this device only (soft-delete with Undo — the Freezr and its real data are untouched). "Join or create another Freezr" from the switcher reuses the exact same choice/join/name/created modals as first-run onboarding, distinguished only by `freezrFlowContext` ('onboarding' vs 'switcher'), which toggles whether a close button/backdrop-dismiss is available and swaps the choice screen's copy.
- **Deleting a Freezr:** a solid-red "Delete this Freezr" button at the bottom of Settings opens a confirmation modal that requires typing the Freezr's own code before the Delete button enables (the typed code *is* the second confirmation — no separate "are you sure" step). Permanent, no Undo, calls `docRef.delete()`. Once a Freezr's document is gone, *any* device's `onSnapshot` firing with no data is now unambiguous evidence of deletion (not a "first run" case — a code is only ever stored locally once its doc is confirmed to exist), handled by `handleFreezrGone()`, which always shows a "Freezr deleted" notice (`freezrGoneModalBack`) before doing anything else: the device that initiated the delete (tracked via a `freezrJustDeletedLocally` flag, since its own listener echoes the deletion back) gets a dismissable success confirmation ("X has been deleted") with a ✕/backdrop-dismiss; any other device gets the same modal but mandatory (no ✕, no backdrop-dismiss — it's news the other person needs to actually see) naming who it was deleted by. Whichever way it's dismissed (Continue, ✕, or backdrop tap) routes through `finishFreezrGoneFlow()`, which is where `switchToAnotherSavedFreezr()` runs: it checks this device's saved-Freezr list (after the deleted one has been removed from it) — if anything's left, it switches straight to the most recently saved one (no re-typing a code); only when nothing else is saved does it fall through to the join/create screen.
- **Barcode scanning:** QuaggaJS (`quagga.min.js` from cdnjs) for live camera scanning, plus a photo-based fallback (`Quagga.decodeSingle` on a photo taken via the native camera app through a file input with `capture="environment"`) — the photo path exists specifically because live browser camera focus/torch control is unreliable across devices (especially iOS Safari), and the native camera app doesn't have that problem. The manual-entry field (Add screen only — removed entirely from Remove mode) takes the item's **name**, not a barcode number (nobody realistically has one memorised); it opens the same "Confirm item" modal used for scans, saves the item with a blank barcode, and — since there's no barcode to key it on — skips the per-barcode `products`/`categoryByBarcode`/`weightByBarcode` "remember for next time" writes entirely. `pendingBarcode === null` means "modal not open"; `pendingBarcode === ''` means "open, no barcode" — don't collapse that back to a truthiness check on `pendingBarcode`, it's the difference between "add" and "silently do nothing."
- **Install gate:** opening the app in a normal browser tab (not installed to the home screen) shows a full-screen, unskippable install-instructions screen (`#installGate`) instead of any app content — detected via `display-mode: standalone` / `navigator.standalone`. Platform-specific: numbered steps for iOS (no install API exists there) and Android (or a one-tap native Install button when the browser's `beforeinstallprompt` fires), a generic "open this on your phone" message elsewhere. A `?dev=1` query-param bypass exists for local testing only — never surfaced in the UI, don't advertise it to real users.
- **Refresh on reopen:** Firestore's `onSnapshot` listener doesn't reliably survive the PWA being backgrounded/suspended by iOS/Android, so a `visibilitychange` listener triggers `location.reload()` once the app has been hidden for 30+ seconds and comes back to the foreground — long enough that a quick glance-away doesn't interrupt an in-progress scan or typed input. This is also what delivers the "Freezr deleted" notice (above) to other devices, and generally what makes new app code / other devices' item changes show up without a manual pull-to-refresh.
- **PWA setup:** `manifest.json`, `service-worker.js`, and icon files (`icon-192.png`, `icon-512.png`, `apple-touch-icon.png`, `favicon.png`) make it installable to the home screen on both Android and iOS.
- **Hosting:** GitHub Pages, static files only, no CI/build pipeline. Deploys are just committing files to the repo root.
- **Navigation:** bottom tab bar with two tabs — **Freezr** (❄️, the original scan/list screen, `#inventoryView`) and **Settings** (⚙️, `#settingsView`). Built to make room for a future third tab (Shopping List is the planned candidate).
- **Categories:** every item has a `category` field (string). `state.categories` is an ordered array of category names — order is user-controlled (drag-to-reorder in Settings) and that order is what every category picker in the app displays. `state.categoryColors` maps category name → hex color. `state.categoryByBarcode` maps barcode → last-used category, the same "learn per barcode" pattern already used for item names (`state.products`), so re-scanning a known barcode defaults to the same category. New item names get a category *guessed* from a keyword dictionary (`CATEGORY_KEYWORDS`/`guessCategory()`) — deliberately simple substring matching, not an LLM call, so the app stays dependency-free and works offline; editable before saving either way.
- **Category picker UI:** collapsed to a single row (current category's colored dot + name + `›` chevron) in the add-item modal, batch review rows, and item detail popup — tapping it opens a shared bottom-sheet (`categorySheetBack`/`openCategorySheet()`) showing the full set of category chips to choose from. This replaced an earlier version that showed all category chips inline at once, which took up too much space (see git history on `feature/compact-category-picker` if the old approach is ever needed for reference).
- **Category colors:** chosen from a fixed 24-swatch preset palette (`CATEGORY_COLOR_PALETTE`), never free-form — this guarantees a color is always re-selectable later. The grid is 6 columns × 4 rows: one column per hue (red/orange/yellow/green/blue/purple) running bright→medium→pastel top to bottom, plus a bottom row of neutrals (black/dark grey/grey/light grey/off-white/brown) for categories with no real hue (e.g. Bakery, Other). New categories default to the grey neutral swatch until the user picks a real color. `normalizeCategoryColors()` runs on every load and silently snaps any stored color that isn't one of the 24 current swatches onto the nearest one (by RGB distance, or the known default if the category name matches) — this exists because the palette itself was introduced *after* categories/colors first shipped, and was later reordered again, so old synced data could otherwise hold colors that no longer appear anywhere in the picker.
- **Theme:** dark (default), light, or "match device", chosen in Settings → Appearance. Stored in `localStorage` (`freezr-theme` key) — deliberately **not** synced via Firestore, since it's a personal per-device display preference, not shared household inventory data. Applied via a `data-theme` attribute on `<html>`, set by a tiny inline script at the very top of `<head>` (before the main CSS) to avoid a flash of the wrong theme on load, then re-applied/kept in sync by the main app script (which also listens for OS theme changes when "match device" is selected).
- **Display name / attribution:** `currentDisplayName`, stored in `localStorage` (`freezr-username`) exactly like the theme preference — asked for via a **mandatory** first-run modal (no skip button, no ✕, no backdrop-dismiss; Continue rejects an empty name) before the app is used at all. Every new item gets `addedBy: currentDisplayName`, shown as "Added by" in the item detail popup only — never on list rows, never searchable/filterable. Editable anytime via a "Your name" field in Settings, which relabels existing items previously logged under the old name.
- **Weight:** every item optionally has a `weight` field — `null`, or `{amount, unit}` where `unit` is one of `g/kg/ml/l/oz/lb` (a real measurement) or `small`/`large` (a container-size placeholder for homemade items with nothing to weigh — picking one of these hides the amount input, since there's nothing to type). `state.weightByBarcode` learns it per barcode exactly like name/category. A best-effort default is parsed from OpenFoodFacts' free-text `quantity` field on a brand-new barcode (`parseWeightGuess()`), only applied if the user hasn't already touched the field themselves. The unit picker is a collapsed row (`renderCollapsedUnit()`) + a shared bottom-sheet (`unitSheetBack`/`openUnitSheet()`) — the same pattern as Category, not a native `<select>` (a styled native dropdown was mocked up and explicitly rejected in favor of this, for looking "plain"/inconsistent with the rest of the app).
- **Freezers:** `state.freezers` is an ordered array of freezer names, seeded with one default (`DEFAULT_FREEZERS = ['Freezer']`). As long as there's only one, the Freezer field is invisible on the add-item screen (items are assigned to it silently) and shown as a plain, non-tappable pill (no picker, no chevron) in the item detail popup. Once a second freezer exists, both places show a tappable pill + the same bottom-sheet pattern as Category/Weight. The freezer picked most recently in a scanning session (`lastUsedFreezer`, an in-memory var, intentionally not persisted) is what the next scan defaults to — deliberately *not* learned per barcode like category/weight, since which freezer something goes in depends on where you're standing, not what the product is. Managed from a "Freezers" Settings page mirroring the Categories page (unique names required, always at least one — delete is disabled on the last remaining row). Deleting a freezer clears its items' `freezer` field to `null` ("not set") *unless* the deletion leaves exactly one freezer remaining, in which case those items — including any already `null` — move to that sole survivor.
- **Filter pills:** a Category pill and a Freezer pill (the latter only shown once 2+ freezers exist) sit above the plain item list; each opens the same picker-sheet pattern as elsewhere with an "All" option added at the top. Both combine with each other and with the search box (AND logic). This is a separate, additive layer on top of the existing "Browse by category" tile view (`state.listView === 'categoryTiles'`/`'categoryItems'`), which is untouched and still works exactly as before — the filter pills only apply while `state.listView === 'items'` or `'history'`.
- **Historical log:** every unit that actually leaves the freezer (scan-to-remove, "Remove from Freezr", or a quantity step-down in the detail popup) is copied into `state.history` as its own entry — one per unit, mirroring the live-item data model — with a snapshot of its name/category/weight/freezer plus `dateRemoved`/`removedBy`, captured via `logRemoval()` *before* the unit is dropped from `state.items`. A 🕘 button opens a dedicated History view (`state.listView === 'history'`) reusing the search box and both filter pills. Units removed together in one action share a single `dateRemoved` timestamp and are grouped into one "×N" row (`groupHistory()`), the same visual language as the live list's own grouping. Each row has a re-add button (pushes new unit(s) back into `state.items`, dated today — falls back to `'Other'`/`null` if the original category/freezer no longer exists) and a remove-from-history button (soft-delete with Undo, same toast pattern used everywhere else). Undoing an *original* removal also un-logs the history entries it created (`unlogRemoval()`), so a mis-scan never shows up in history at all. `state.history` is unbounded — nothing prunes or caps it yet (see design-decisions note below).

## Important design decisions (don't "fix" these — they're deliberate)

- **`service-worker.js` is intentionally a no-op** — it registers a `fetch` listener but never calls `respondWith()`. This exists purely to satisfy Android's install criteria. It does NOT cache anything, on purpose: aggressive caching previously caused stale-version bugs, and since the app is useless offline anyway (needs live Firestore), there's no upside to caching.
- **Data model:** `state.items` is a flat array of individual unit records (`{id, barcode, name, category, weight, freezer, dateAdded, opened, addedBy}`), NOT pre-grouped by quantity. The UI groups same barcode+name into one row with a "×N" badge at render time (`groupItems()`), but removal/quantity operations always work FIFO against the oldest individual unit. This was a deliberate choice to keep removal logic simple and consistent. `state.history` follows the same one-record-per-unit shape (see Architecture above), for the same reason.
- **The historical log grows unbounded — nothing prunes or caps `state.history`.** Everything in this app lives in one Firestore document (see Storage/sync above), which has a hard size limit; a household that never clears old history could theoretically hit it someday. Not solved, not urgent at household scale — just don't assume it's been thought through if it ever comes up.
- **The item detail popup uses staged edits.** Name, quantity, and opened/sealed status are all held in local variables (`pendingQty`, `pendingOpened`, the name input's value) and only committed to `state.items` when Save is tapped. Close/✕ discards everything. This was a bug fix — quantity used to apply live immediately while name didn't, which was confusing and got explicitly fixed.
- **Opened/sealed status applies to the *oldest* unit in a group**, not per-unit, since the UI only exposes one toggle per grouped row. Documented simplification, not a bug.
- **Versioning scheme (semantic, restarted from 1.0.0):** `x.0.0` = major (genuinely new features/pages), `1.x.0` = minor (batches of smaller additions), `1.0.x` = patch (tiny fixes/tweaks). The version number is hardcoded in the footer of `index.html` and must be bumped by hand with every change. Full history lives in `CHANGELOG.txt` — update both together, every time.
- **Icons must be full-bleed square PNGs with square corners in the source file** — never round the corners yourself. iOS/Android apply their own mask on top, so a pre-rounded icon causes double-rounding/white-sliver artifacts. Learned this the hard way.
- **Firebase web API keys are not secret** — they're meant to be public in client-side code. Security comes from Firestore rules, not from hiding the key. The GitHub repo is public and that's fine.
- **Category drag-to-reorder uses Pointer Events, not native HTML5 drag-and-drop.** iOS Safari — the primary target device — doesn't fire native `dragstart`/`dragover` events for touch input, so a native-DnD implementation would silently not work on iPhone. The reorder logic (`attachCategoryDragHandlers()`) tracks `pointerdown`/`pointermove`/`pointerup` on a drag handle, visually follows the pointer via `transform: translateY()` on the dragged row, computes the target index by comparing the dragged row's live midpoint against sibling rows' static midpoints, and only commits the array reorder + full re-render on release.
- **Toast z-index must stay above modal z-index.** The toast was originally `z-index: 50` while modals are `z-index: 60`, so any validation toast fired while a modal was open (e.g. "That category already exists") rendered invisibly behind the modal — it looked like the action silently did nothing, when it had actually correctly been rejected. Fixed by raising the toast to `z-index: 70`. If a new overlay is ever added above modals, keep the toast above it too, or this bug comes back.
- **All local testing of `index.html` in this environment must use a stub Firestore, not the real one.** The sandbox this app has been developed in blocks outbound requests to `www.gstatic.com` and `cdnjs.cloudflare.com` (org network policy — 403, not a trust/cert issue), so Firebase and Quagga can't load in a real browser here. The working pattern: copy `index.html` to a throwaway file, replace the two Firebase `<script>` tags with a single `<script src="fake-firebase.js">` (a small in-memory Firestore emulator — `onSnapshot`/`.set()`/`.delete()` with `merge` support is enough to exercise the real app logic unmodified), serve both over a local `python3 -m http.server`, and drive it with Playwright (`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`, `/opt/node22/lib/node_modules/playwright`), passing `?dev=1` to bypass the install gate. Delete the throwaway files afterward — never commit them. This has been the standard verification step for every feature/fix in this project so far. **For a scenario needing two genuinely independent devices** (e.g. verifying a Freezr-deletion notice propagates to another device) the single-page/localStorage-backed stub isn't enough — two Playwright pages in the same browser context still share localStorage, so a change on one silently leaks into the "other device" and produces false results. Use two separate browser *contexts* instead (real separate storage each), backed by a tiny shared polling server (a `fake_server.py` HTTP endpoint holding the store, with `fake-firebase.js` using `fetch()` + a ~200ms poll loop instead of localStorage) so both contexts talk to the same simulated backend the way two real devices would talk to the same real Firestore.
- **An empty string and "not set" are different states, not the same falsy thing.** `pendingBarcode` in the add-item modal: `null` = modal not open, `''` = open with deliberately no barcode (manual name entry). A naive `if (!pendingBarcode)` guard treats both the same and silently breaks manual add — check `=== null` specifically when "is the modal/flow active at all" is the real question.
- **Deleting a Freezr auto-switches to another saved Freezr when one exists** (`switchToAnotherSavedFreezr()`, added in v9.0.1 at the user's request — this used to deliberately always land on join/create, don't revert it back). Both the device that deletes it and any other device that discovers the deletion pick the most recently saved remaining Freezr, if there is one; join/create is only shown when this device has nothing else saved.
- **The device that deletes a Freezr now sees a confirmation before anything switches** (v9.0.2, at the user's request — this used to skip straight to the switch/join-create with no acknowledgment at all). Typing the code and tapping Delete is still the only confirmation *step*, but the "Freezr deleted" notice (`freezrGoneModalBack`) now always shows first, dismissable via ✕/backdrop/Continue for the device that did the deleting; the switch to another saved Freezr (or fallback to join/create) only happens once that notice is dismissed, via `finishFreezrGoneFlow()`. The mandatory, non-dismissable version of the same modal for a device that merely discovers someone else deleted it is unchanged.

## Known issues (unresolved, don't re-litigate without new info)

- **Safari Share-button JS error:** tapping the native iOS Share icon sometimes triggers a generic, detail-free "Script error." in the page's error banner. Extensively debugged (ruled out the async Firestore render path, ruled out the service worker) — it's very likely an opaque/masked error from something Safari itself does internally (e.g. generating the share preview), not app code. Doesn't affect any real functionality. Worth revisiting only with real Safari devtools access (e.g. via a Mac), not by guessing blind again.
- **Camera focus on some Android devices** can be unreliable through the browser (this is *why* the photo-scan fallback exists). Native camera APIs (if this ever becomes a Capacitor-wrapped native app) would likely fix this properly.
- **The toast can silently intercept taps even while hidden.** `.toast` is `position:fixed` with `opacity:0` when not showing, but has no `pointer-events:none` in that state — it still occupies its layout box at a fixed screen position and can absorb a real click/tap landing there, even though nothing is visible. Surfaced while writing Playwright tests (synthetic coordinate-based clicks on buttons near the toast's position were silently swallowed until switched to dispatching a real DOM `.click()` instead), not confirmed to bite real users, but plausible on a real device if a button happens to sit where the toast appears. Fix would be a `pointer-events: none` on the non-`.show` state — not done yet since it's never been confirmed as a real user-facing problem.

## Possible future direction: native app packaging

If this ever needs to go on the Play Store / App Store, the current architecture carries over directly — no rewrite needed:
- **Android:** Trusted Web Activity (Google's official PWA→Play Store path), lightweight.
- **iOS:** Capacitor wrapper + Apple Developer account + App Store review. Would also likely fix the camera focus/torch limitations above via native camera APIs.
This isn't being actively pursued — just documented so it's not forgotten as an option.

## Working conventions

- Keep everything in as few files as practical. Don't introduce a build step/bundler/framework without a strong reason — this is meant to stay simple enough for a non-developer to redeploy by hand if needed.
- Bump the version number + `CHANGELOG.txt` with every change, however small.
- See `freezr-app-ideas.md` in this repo for the full backlog of planned/considered features (organized into Done / Known issues / Organisation / Bigger features / Ideas). Check it before assuming something hasn't been discussed.
- **"Freezer" vs "Freezr" — these are not interchangeable.** "Freezer" is the physical appliance (or one of several, once multiple freezers exist) — the thing a unit of food is physically kept in. "Freezr" is the shared household inventory as a whole — the join-by-code group everyone's data lives in (see "Freezr households" above). In UI copy: you add/remove things **to/from Freezr** (the inventory — e.g. the existing "Remove from Freezr" button, and the shopping list's "Add to Freezr" action), but you **choose which Freezer** something goes in (the physical picker/field, e.g. "Select a freezer"). When in doubt, ask: is this about the inventory action, or about which physical box the item sits in?
- **Git workflow used throughout this project:** one feature/fix per branch, cut from the latest `main` each time (never stacked on a previous feature branch once it's merged — check whether the last PR merged before branching). Push, open a PR with a Summary + Test plan (the test plan documents what was verified with the stub-Firestore Playwright setup above), and wait for the user to merge via the GitHub UI before starting the next branch. The user does the merging; don't merge PRs unprompted.
- **For any visually/interactively significant UI change (new layout, new component, reworked interaction), build a working mockup as a published Artifact first and get explicit sign-off before touching `index.html`.** This has come up repeatedly (the collapsed category-picker-with-sheet redesign, the 6×4 color grid reorder, the Freezr onboarding/switcher/delete-confirmation flows, the install gate) and the user has explicitly asked for it by name ("show me what it will look like before making changes"). Match the mockup's HTML/CSS to the app's real tokens and structure (pull actual hex values and markup from `index.html` rather than approximating) so what's approved is literally what gets built — expect at least one round of feedback (button fill vs. outline, trimmed copy, etc.) before it's approved, and republish to the same Artifact URL rather than a new one. Small, unambiguous bug fixes (e.g. the toast z-index issue) don't need this — only genuine design decisions do.

"Join or create another Freezr" from the switcher reuses the onboarding modals with a close button added.

Paired with a fix for the app only picking up new data/code on manual pull-to-refresh: it now reloads itself automatically after being backgrounded 30+ seconds and brought back to the foreground, which is also what delivers the "this Freezr no longer exists" notice to other devices after a deletion.
